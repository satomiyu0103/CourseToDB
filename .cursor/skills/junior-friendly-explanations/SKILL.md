# ジュニア向け用語解説

## 前提

利用者はプログラミング・IT を学び始めた段階。  
「`notion_client.py` は公開 API 不変の facade」のように **専門用語だけ並べると伝わらない**。

チャットでは **用語 → 平易な日本語 →（必要なら）たとえ** の順で書く。

## いつ適用するか

- コード・設計・Git・テスト・リファクタの説明
- 実装完了報告・計画の要約
- 利用者が「意味を教えて」「分からない」と言ったあとのフォロー

**省略してよい**: CHANGELOG 1行、コミットメッセージ、リポジトリ内 doc 本文（別ルールが正本）

## 書き方テンプレ

### 用語1つのとき

```markdown
**用語（読み）** — 平易な定義（1文）。
たとえ: …（任意・短く）
```

### 設計変更を報告するとき

1. **やったこと**（何が変わったか）
2. **用語の解説**（文中の専門語それぞれ）
3. **利用者への影響**（操作やファイルの触り方が変わるか）

## 例（本リポジトリ）

### 悪い例

> `notion_client.py` は公開 API 不変の facade。`clients/notion/` に責務分割した。

### 良い例

> **やったこと**: Notion 用のコードを小さなファイルに分けました。表向きの入口ファイル `notion_client.py` は残しています。
>
> - **facade（ファサード）** — 建物の「正面入口」のような、**外から見える窓口だけ** のこと。中身は別ファイルに分かれていても、使う側は `NotionClient` だけ覚えればよい、という形です。
> - **公開 API（こうかいエーピーアイ）** — 他のプログラムから呼び出せる **メソッド名・引数の約束**。`fetch_events()` など、名前と使い方を変えていない、という意味です。
>
> **影響**: `sync` や `import` の使い方は変わりません。中身の整理だけです。

## よく出る用語（初出時は解説）

| 用語 | 解説の骨子 |
|---|---|
| API | プログラムが外部サービス（Notion 等）とデータをやり取りする窓口 |
| クラス / モジュール / 関数 | コードの入れ物の大・中・小。ファイル＝モジュール、関数＝処理の1かたまり |
| import | 別ファイルの機能をこのファイルで使う宣言 |
| リファクタ | 動きは同じに、読みやすく整理すること |
| テスト | 自動で「期待どおり動くか」を確認するコード |
| mock（モック） | 本物の API の代わりに、テスト用の偽の応答を使うこと |
| PR / ブランチ | 変更を分けてレビュー・統合する Git の仕組み |
| 委譲（いにん） | 自分で全部やらず、別の部品に処理を渡すこと |
| 型 | データの種類（文字列・日時・リスト等）の約束 |
| 例外 | エラー時にプログラムが投げる「失敗の知らせ」 |

一覧にない用語も **初出で必ず** 同様に解説する。

## トーン

- です・ます調、丁寧だが説教臭くしない
- 「当たり前ですが」は使わない
- 分からないことを責めない
- 長くなりそうなら、先に結論1文 → 用語解説 → 詳細の順
